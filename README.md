# 理小办 · 校园办事智能体（可运行原型站点）

大连理工大学「连小理」新生智能体应用与设计大赛 · 赛道一：智能体创意应用

> 我们不是让 AI 替学生搜索信息，而是让 AI 理解学生的目标，
> 帮学生从「不知道怎么办」走到「知道下一步做什么」。

## 一、这是什么

一个**真实可运行**的功能原型网站。首页中部的核心演示区接住了「三段接力」的完整链路：

```
提问 → ① 信息智能体（查得准）→ ② 规划智能体（排得顺）→ ③ 执行助手（做得成）→ 🧠 理小办收口 → 办事卡
```

选好校区后，用日常说法提问（例如「我的校园卡丢了怎么办」「寝室空调不制冷」「屋里突然没电了」），
三段输出会**依次生成并实时渲染**，最后由「理小办」收口成一张办事卡。

## 二、怎么打开

纯静态站点，无依赖、无构建、无需联网。

**方式 A（推荐）**：起一个本地静态服务

```bash
cd lixiaoban-site
python -m http.server 8848
# 浏览器打开 http://127.0.0.1:8848
```

**方式 B**：直接双击 `index.html`
三个 JS 均用 `<script src>` 引入（不用 ES module、不用 fetch JSON），因此 `file://` 协议下也能正常工作。

**分享某张卡**：`?q=` + `&campus=` 深链会自动运行并滚动到演示区，例如

```
index.html?q=我的校园卡丢了怎么办&campus=盘锦校区
```

## 四、为什么这样实现

### 1. 用规则引擎而不是大模型

本站**未调用任何大模型**。所有答案由 `engine.js` 在 `data.js` 的真实依据库上推演得出，因此：

- 结果**可复现**，同一句提问永远得到同一张卡；
- 每条事实都**带出处**，不存在模型编造推测内容的风险；
- 契合赛事「不得虚构对话与使用过程」的合规要求。

它实现的是三智能体的**职责边界与产物形态**，这也是方法论里真正可迁移的部分。

### 2. 命中不了的就如实说命中不了

遇到检索域外的问题（如「明天天气怎么样」），站点**明确回答未覆盖**并给出可选方向，
而不是生成一个看起来合理的答案。

匹配采用三层打分，低于阈值（26）即判定未命中：

| 信号 | 说明 |
|---|---|
| 包含匹配 | 学生的话直接包含（或被包含于）某条语料 |
| 二元组相似度（Dice） | 兜底「卡找回来了还能用吗」这类相似但不互相包含的说法 |
| 关键词加权 | 场景词 + 动作触发词共同加权 |

> **这里踩过一个坑**：仅用相似度兜底时，「图书馆几点关门」「怎么选课」「四六级什么时候报名」
> 会被误判进相近意图。解决办法是给相似度加了**动作触发词闸门**——
> 只有句中真的出现「坏了 / 丢了 / 请假 / 没电」这类问题信号时才允许兜底。
> 详见 `data.js` 中每个 intent 的 `triggers` 字段。

### 3. 校区差异是真的在起作用

「地点」类字段按校区取值，`PLACE` 模板里有三校区各自的服务大厅：
凌水（网信中心一楼东门，工作日 08:00–15:00）、开发区（七舍二楼西侧自助服务中心）、盘锦（G01 行政楼二楼）。
切换校区，办事卡的地点栏会随之改变。

|---|---|---|---|
| 校园卡丢失补办 | 已实跑 | 4 份 | 3（挂失补办 / 解挂 / 拾得） |

| 学生证补办 | 草稿 · 待实跑 | 1 份 | 1 |

草稿场景在卡片上带**黄色徽章**，字段里的【待核实】占位会**高亮显示**，明确提示不可直接照办。

## 六、怎么加一个新场景

架构与输出格式**完全不变**，只改 `data.js`，在 `scenarios` 数组里追加一个对象即可：

```js
{
  id: 'xxx', name: '场景名', short: '简称',
  status: '草稿 · 待实跑',          // 先标草稿，实跑后再改
  domain: '检索域说明',
  oneLine: '一句话描述', target: '适用人群',
  draft: true,                      // 草稿为 true，会启用【待核实】提示
  sources: [ { name, scope, fact, source, verified: '待核实' } ],
  facts:   [ { fact, source, campus } ],
  intents: [ {                       // 一个 intent = 一条办事路径
    id: 'xxx', canonical: '规范问法',
    keywords: ['场景词'],            // 打分用
    triggers: ['坏了', '怎么办'],     // 闸门用：必须是「问题/动作」信号
    phrases: ['学生实际说法1', '模糊说法2'],
    conclusion: (c) => `结论先行文案`,
    steps: [ { n: 1, title, detail, branch, elements: { entry, place, material, caution } } ]
  }],
  openItems: ['还没核实的事项，不许凭推测填']
}
```

对应「场景迁移三步法」：

| 步骤 | 在配置里改哪里 |
|---|---|
| 换检索域 | `sources` + `facts` + `domain` |
| 换执行字段 | 各 step 的 `elements` 四要素（`place` 可写成按校区取值的对象） |
| 换真实问法 | 各 intent 的 `phrases`（务必写学生真会说的话，不是流程术语） |

## 七、数据纪律（改动时务必遵守）

1. 每条事实必须**带出处**；未核实的字段保留 **【待核实】**，不得凭推测填入。
2. 场景状态区分「已实跑 / 已出规格 / 草稿」，未验证的不得标为已验证。
3. 未实测的效果数据一律 **【待填】**，不写估算值。站点「应用效果」区的四个指标即遵循此条。
4. 引用的规定名称、地点、费用、时限，上线前需核对至最新版本。
